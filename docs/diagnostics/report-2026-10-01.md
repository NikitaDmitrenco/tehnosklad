## 3. Цепочки причин (шаг 3)

### B1

- **а) Код — да, подтверждено.** UI: `src/components/admin/admin-forms.tsx:90-95` — `CountedInput maxLength={70}` (`:92`), `:104-109` — `CountedTextarea maxLength={160}` (`:106`); компонент общий (`TranslationFields`) для RU и RO категорий и товаров. Браузер обрезает ввод по HTML `maxLength` — исключение не возникает, «падения» нет; несоответствие молчаливое. Живой DOM подтверждает (§2б, B1).
- **б) Данные/входные ограничения — да.** 70/160 против 180/320; DB CHECK `≤180/≤320` (`supabase/migrations/20260805111516_initial_schema.sql:67-69` категории, `:110-112` товары); доки `ADMIN_GUIDE.md:202-203` (категории) и `:447-448` (товары). Связанный конфликт DOC-03: category name UI 240 (`admin-forms.tsx:42`) vs DB CHECK 160 (`initial_schema.sql:60`) — при длине 161–240 сервер примет, БД ответит CHECK 23514 → generic `operation_failed` (цепочка B3, фактор «а»).
- **в) Лимиты платформ — не причина.** Текстовые поля не связаны с лимитами Vercel/Supabase; `serverActions.bodySizeLimit` не участвует. Не проверено: ничего (фактор неприменим).
- **г) Права/сессия — не причина (да, проверено: работает).** Форма открывается после `requireAdmin()` (`src/features/admin/auth/guard.ts:40-44` → redirect `/admin/login`); логин в диагностике работал. На баг влияния нет.

- **е) Состояние/время — не причина.** Статический атрибут, гонок нет.
- **ж) Сеть/внешние сервисы — не причина.** Не проверено? Проверять незачем: атрибут рендерится серверным RSC, сеть не участвует (да, проверено — данные из DOM).
- **з) Локализация — не причина.** Один `TranslationFields` на обе локали: 70/160 одинаковы для RU и RO (DOM-вывод §2б). Админка в целом RU-only (см. §4).

## 4. Общий раздел: как сейчас устроена обработка и показ ошибок

**1. Admin (backoffice) — единый механизм «redirect + query-код + баннер».**

- Каждая server action всегда делает `redirect(destination(path, error))`: `destination()` либо `?saved=1`, либо `?error=<код>` (`src/features/admin/actions.ts:45-50`); код даёт `actionCode()` (`:39-43`): `AdminValidationError` → фиксированный `validation`, всё остальное → `sanitizeAdminError().code`. Сырые тексты Postgres/UI не покидают сервер (в JSX `err.message` не рендерится — grep 0 вхождений).

**Файл 4,6–5 МБ при `bodySizeLimit: "6mb"` — вывод:**

1. Платформенный лимит Vercel (4.5 MB) действует **до** Next.js и до `validation.ts:141`. Файл 4,6–5 МБ (в т.ч. «легальный» для приложения 5242880) на проде упирается в **413 `FUNCTION_PAYLOAD_TOO_LARGE`**: server action не выполняется, redirect с `?error=` не происходит → пользователь **не увидит** сообщение «Файл должен быть JPEG… до 5 МБ», а получит сбой загрузки (как именно UI отрисует 413 — error boundary «Не удалось загрузить раздел» или сетевая ошибка формы — **гипотеза, на проде не проверено**).
2. `serverActions.bodySizeLimit: "6mb"` в этой конфигурации ситуацию не спасает: платформа строже.
3. Единица «4.5 MB» в доке Vercel не расшифрована: при decimal (4 500 000 Б) отклоняется весь диапазон 4,6–5 МБ; при binary (4 718 592 Б) — файлы ≳4,72 МБ, а 4,6–4,7 МБ могут пройти. Обе интерпретации честно указываем.
4. Локально (`next start`, без Vercel) платформенного лимита нет: 5 МБ доходят до `validation.ts:141` — **локальное поведение ≠ прод** (подтверждено прогонами: oversize-файл доходил до приложения и получал `validation`).
5. Telegram: лимит соблюдён жёстким `slice(0,4090)`; известный edge — финальный slice может обрезать посреди HTML-сущности → `parse_mode: HTML` reject (**гипотеза, не воспроизводилось**; практический риск низкий — фиксированные поля сообщения малы).
