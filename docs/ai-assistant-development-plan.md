# План развития AI-ассистента Техносклада

## Цель

Создать ассистента, который корректно обрабатывает максимально широкий спектр вопросов пользователей и в каждом случае выдаёт один из трёх безопасных результатов:

1. Точный ответ, основанный на достоверном источнике.
2. Уточняющий вопрос, если исходных данных недостаточно.
3. Честное объяснение ограничения и подходящий следующий шаг: открыть каталог, позвонить в магазин, оставить заявку или обратиться к сотруднику.

Гарантировать содержательный ответ буквально на любой возможный вопрос нельзя. Поэтому задача системы — не только отвечать, но и правильно распознавать ситуации, когда ответ неизвестен, неоднозначен, требует актуальной проверки или выходит за пределы компетенции магазина.

## 1. Определить область знаний

Необходимо перечислить основные категории пользовательских вопросов:

- адрес, телефон и график работы;
- товары, категории и бренды;
- цены и наличие;
- подбор техники по требованиям;
- сравнение моделей;
- характеристики и совместимость;
- доставка и самовывоз;
- оплата, кредит или рассрочка;
- гарантия, возврат и обмен;
- установка и подключение;
- статус заказа;
- контакты и обращения;
- общие вопросы о компании;
- вопросы, не относящиеся к магазину.

Для каждой категории необходимо определить официальный источник информации.

| Категория вопроса      | Достоверный источник                  |
| ---------------------- | ------------------------------------- |
| Адрес, телефон, график | Публичные настройки сайта             |
| Цена и наличие         | База данных каталога                  |
| Характеристики         | Карточка товара                       |
| Доставка и оплата      | Настройки или информационные страницы |
| Гарантия и возврат     | Утверждённые документы магазина       |
| Статус заказа          | Защищённый серверный API              |
| Общие вопросы          | Контролируемая база знаний            |
| Неизвестный вопрос     | Уточнение или перевод на сотрудника   |

## 2. Создать единую публичную базу знаний

Сейчас ассистент в основном опирается на каталог товаров. Необходимо сформировать общий публичный контекст магазина, который может включать:

- название компании;
- адрес;
- номер телефона;
- рабочие дни и часы;
- способы оплаты;
- условия доставки и самовывоза;
- правила гарантии, возврата и обмена;
- доступные услуги;
- обслуживаемые населённые пункты;
- ответы на часто задаваемые вопросы;
- данные опубликованных товаров.

Следует создать отдельный публичный слой данных с белым списком разрешённых полей. Модели нельзя передавать:

- API-ключи и секреты;
- персональные данные клиентов;
- заявки других пользователей;
- административные данные;
- внутренние комментарии;
- себестоимость и закрытые поля;
- системные и служебные инструкции.

## 3. Добавить определение намерения пользователя

Перед подготовкой ответа система должна определить тип вопроса. Возможные намерения:

- `store_info` — адрес, телефон и график;
- `product_search` — поиск товара;
- `product_comparison` — сравнение моделей;
- `delivery` — доставка и самовывоз;
- `payment` — оплата и рассрочка;
- `warranty` — гарантия, возврат и обмен;
- `order_status` — статус заказа;
- `lead` — звонок или заявка;
- `general` — общий вопрос;
- `out_of_scope` — вопрос вне компетенции магазина.

Определять намерение можно правилами, отдельной небольшой моделью или основной моделью со строгим JSON-ответом.

Маршрутизация необходима, чтобы система не искала адрес магазина среди товаров и не обращалась к генеративной модели там, где можно вернуть точное значение из базы данных.

## 4. Отдавать критичные факты без генерации AI

Для точных и часто изменяющихся данных следует использовать детерминированные серверные обработчики:

- «Где находится магазин?» — получить `address` из публичных настроек;
- «Какой номер телефона?» — получить `phoneDisplay`;
- «Когда вы работаете?» — получить рабочие дни и часы;
- «Есть ли товар в наличии?» — проверить актуальный статус в каталоге;
- «Сколько стоит модель?» — получить текущую цену из базы.

AI может формулировать итоговый текст, но не должен самостоятельно вспоминать или придумывать значения. Источником истины остаётся база данных.

## 5. Использовать RAG для сложных информационных вопросов

RAG — это поиск релевантной информации перед обращением к модели.

Пример обработки вопроса о возврате:

1. Пользователь спрашивает, можно ли вернуть неподошедший товар.
2. Система определяет намерение `warranty`.
3. Поиск находит соответствующие фрагменты официальных правил.
4. Модели передаются только найденные фрагменты.
5. Модель формирует понятный ответ без добавления неподтверждённых условий.
6. Пользователь получает ссылку на полную версию правил.

Для каждого фрагмента базы знаний желательно хранить:

- источник;
- язык;
- дату обновления;
- уровень доверия;
- ссылку на страницу;
- версию документа.

## 6. Реализовать структурированный поиск по каталогу

Для подбора техники недостаточно обычного текстового поиска. AI должен преобразовывать запрос пользователя в структурированные фильтры.

Например, запрос «Нужен холодильник до 12 000 леев, шириной не больше 60 см, желательно No Frost» должен преобразовываться примерно в следующую структуру:

```json
{
  "category": "refrigerators",
  "maxPriceMinor": 1200000,
  "attributes": {
    "widthMaxCm": 60,
    "noFrost": true
  }
}
```

После этого сервер выполняет поиск по реальным опубликованным товарам. AI объясняет различия между найденными позициями, но не создаёт несуществующие модели, цены или характеристики.

## 7. Добавить инструменты для действий

Ассистент должен уметь не только отвечать текстом, но и предлагать или выполнять разрешённые действия:

- открыть каталог с подготовленными фильтрами;
- открыть карточку товара;
- показать контакты;
- инициировать звонок;
- открыть форму заявки;
- заполнить заявку после подтверждения пользователя;
- показать маршрут до магазина;
- проверить наличие;
- сравнить выбранные товары.

Каждый инструмент должен иметь строгую схему входных параметров. Любое действие, связанное с отправкой персональных данных или созданием заявки, необходимо выполнять только после явного подтверждения пользователя.

## 8. Полноценно использовать историю разговора

Историю необходимо передавать модели в безопасном и ограниченном виде. Это позволит понимать уточняющие вопросы.

Пример:

> Пользователь: Покажи холодильники до 10 000 леев.
>
> Ассистент: Нашёл три модели.
>
> Пользователь: Какая из них самая узкая?

В последнем вопросе выражение «из них» относится к ранее найденным товарам. Без истории ассистент не сможет корректно определить контекст.

При этом история разговора не должна считаться источником фактов. Источниками истины остаются база данных, настройки и официальные документы.

## 9. Научить ассистента задавать уточняющие вопросы

Если запрос неоднозначен, ассистент не должен угадывать предпочтения пользователя.

Например, на запрос «Нужна хорошая стиральная машина» следует спросить:

- максимальный бюджет;
- желаемую загрузку;
- допустимую ширину или глубину;
- важные функции.

Для разных категорий можно определить рекомендуемый набор уточнений:

- холодильник — бюджет, размеры, объём, тип разморозки;
- стиральная машина — бюджет, загрузка, глубина;
- кондиционер — площадь помещения и особенности установки;
- телевизор — диагональ, бюджет, разрешение и Smart TV.

## 10. Ввести правила достоверности

Ассистент должен соблюдать следующие правила:

- не придумывать товары;
- не придумывать цены;
- не обещать наличие без проверки базы;
- не выдумывать условия доставки;
- отделять подтверждённый факт от рекомендации;
- сообщать, когда информация требует подтверждения;
- предлагать связаться с магазином при недостатке данных;
- не подтверждать совместимость без надёжного источника;
- не давать юридических или финансовых гарантий.

Ответ сервера желательно возвращать в структурированном виде:

```json
{
  "answer": "Магазин находится по адресу ...",
  "intent": "store_info",
  "confidence": "high",
  "sources": ["site_settings"],
  "productIds": [],
  "actions": [
    {
      "type": "open_map"
    }
  ]
}
```

## 11. Разделить ответы по уровню уверенности

Можно использовать три уровня уверенности:

- `high` — значение получено напрямую из базы данных;
- `medium` — ответ сформирован по найденному официальному документу;
- `low` — данных недостаточно или запрос неоднозначен.

При низкой уверенности ассистент не должен выдавать предположение как факт. Он должен задать уточняющий вопрос или предложить обращение к сотруднику.

## 12. Определить правила работы с внешними вопросами

Необходимо заранее решить, разрешено ли ассистенту использовать интернет для вопросов, не покрытых внутренней базой знаний.

Возможны два режима:

1. Ассистент отвечает только по данным магазина.
2. Ассистент может использовать внешние источники, но явно отделяет внешнюю информацию от данных магазина и показывает ссылки.

Если внешний поиск разрешён, нужны:

- белый список надёжных источников;
- ссылки на использованные материалы;
- проверка даты публикации;
- защита от вредоносных инструкций на сторонних страницах;
- запрет автоматически переносить внешние цены и наличие в каталог.

## 13. Безопасно обрабатывать вопросы о заказах

Ассистенту нельзя предоставлять произвольный доступ ко всей таблице заказов.

Безопасный процесс может выглядеть так:

1. Определить намерение `order_status`.
2. Запросить номер заказа.
3. Выполнить проверку личности, например по телефону или одноразовому коду.
4. Получить только разрешённые поля конкретного заказа.
5. Вернуть статус без раскрытия лишних персональных данных.

## 14. Добавить журналирование и аналитику

Для развития ассистента следует сохранять обезличенные технические показатели:

- тип вопроса;
- был ли найден источник;
- использовался ли резервный ответ;
- какие документы или категории были найдены;
- время ответа;
- оценку пользователя;
- причину неудачи;
- был ли переход в каталог или создана заявка.

Особенно полезно собирать вопросы, на которые ассистент не смог ответить. Они покажут, каких данных и сценариев не хватает в базе знаний.

Полные персональные данные и секретную информацию без необходимости сохранять нельзя.

## 15. Подготовить автоматические проверки

Перед публикацией необходимо создать набор сценариев на русском и румынском языках:

- адрес, телефон и график;
- поиск и подбор товаров;
- сравнение моделей;
- доставка, оплата и гарантия;
- отсутствие подходящих товаров;
- неоднозначные вопросы;
- уточняющие вопросы;
- попытка получить административные данные;
- попытка заставить AI игнорировать инструкции;
- вопросы с ошибками и разговорными формулировками;
- вопросы на смешанном русском и румынском;
- недоступность AI-провайдера;
- устаревшая или противоречивая информация.

Отдельно необходимо проверять, что AI не выдумывает товары, цены, наличие, контакты и условия обслуживания.

## 16. План поэтапной реализации

Рекомендуемый порядок работ:

1. Передать ассистенту публичные настройки: адрес, телефон и график.
2. Добавить прямые обработчики контактных вопросов.
3. Начать полноценно использовать историю диалога.
4. Добавить маршрутизацию намерений.
5. Создать базу знаний по доставке, оплате, гарантии и возврату.
6. Добавить RAG-поиск по базе знаний.
7. Реализовать структурированный подбор товаров.
8. Добавить действия: фильтры, сравнение, звонок и заявка.
9. Внедрить оценку уверенности и ссылки на источники.
10. Добавить тесты, журналирование и панель неотвеченных вопросов.

## Основной архитектурный принцип

Генеративная модель не должна быть самостоятельным источником информации. Она должна понимать вопрос, выбирать подходящий сценарий и формулировать ответ. Факты необходимо получать из контролируемых источников:

- базы данных каталога;
- публичных настроек магазина;
- официальных документов;
- базы знаний;
- безопасных серверных инструментов.

Такая архитектура позволит расширить круг поддерживаемых вопросов, снизить количество выдуманных ответов и обеспечить актуальность критичных данных.
